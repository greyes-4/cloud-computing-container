Recovery-Time Analysis
During the chaos tests, the Uploader recovered in 74.3 seconds, passing the 180-second SLo, while the viewer recovered in 83.7 seconds but failed the 20-second SLO. Both of these applications went down approximately five seconds after their instances were terminated. Most of the their recovery time appeared to come from AWS launching replacement EC2 instances and starting the applications, including installing Node.js and its dependencies. The ALB health check also contributed to the recovery windows but the short 10 seconds intervals helped reduce ant detection delays. Based on the results I got, instance replacement and application startup were most likely the biggest factors, although the test did not measure each step separately. And using a preconfigured AMIs or keeping an additional healthy instance could also help in reducing recovery time. 

Chance to the Create and Delete Scripts
Compared with Lab03, the main change to create_app_stack.sh was changing the direct aws ec2 run-instances commands with Auto Scaling Groups. Instead of launching all the instances manually, the script can now create two ASGs that can automatically maintain and replace one EC2 instance per application while also using the existing launch templates. It can also create an Application Load Balancer, two target groups, listeners on ports 8080 and 8081, and security groups rules that allow the ALB to communicate with te applications. The delete_app_stack.sh script was also updated to delete the Auto Scaling Groups and their EC2 instances first which was then followed by the ALB, target groups, security groups, launch templates, IAM resources, and the S3 bucket. With these changes, it allowed the applications to recover automatically when an instance fails.
